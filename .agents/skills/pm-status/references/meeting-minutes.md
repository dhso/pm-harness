# 会议纪要确认与项目联动

会议纪要不只是文档，也是后续项目更新的证据入口。先确认记录准确，再把结论应用到结构化事实源；不要让信息只停留在 Markdown 中。

## 纪要状态

- `draft`：根据会议、录音转写、聊天或个人记录整理，内容尚未确认。
- `pending_confirmation`：结构已经完整，但仍有参与人、数字、日期、责任人或结论需要确认。
- `confirmed`：用户确认纪要准确反映会议内容，并记录确认人和确认时间。

“纪要已确认”只证明记录准确，不自动证明其中每项业务决定都经过授权。批准人、审批范围和用户对批准事件的确认仍按 Harness 护栏单独核对。

## 从会议内容提取项目事项

逐项区分讨论、事实、决定、行动、需求、计划影响、风险、问题和待确认项：

| 会议内容 | 项目处理 |
|---|---|
| 已发生的工作或结果 | 更新活动、任务实际时间、进度和证据 |
| 新行动项 | 新建或更新任务，记录负责人、日期、依赖和下一步 |
| 新需求或反馈 | 记录为候选或提议需求，并关联纪要来源 |
| 修改已批准需求、范围或验收 | 需求替代使用 `requirement.replacement.propose` 原子生成候选与变更请求，批准后再应用替代关系 |
| 新的预计日期 | 更新 forecast，保留 baseline |
| 修改承诺日期或时间基线 | 创建变更请求并获得 `schedule_baseline` 范围批准 |
| 风险、问题或阻塞 | 更新登记册、负责人、影响和应对动作 |
| 决策 | 无有效权限时保持 `proposed`；有权限且用户确认审批确已发生后才记为 `approved` |
| 交付安排 | 更新交付物计划或评审状态；不能据此声称已交付或已验收 |

讨论中的日期要区分目标、预测和承诺。没有明确责任人的行动项标为 `unassigned`，没有明确决定的选项保留为待确认。

## 应用顺序

1. 将会议原始材料登记为来源；录音、截图和完整转写进入本地归档。
2. 用 `templates/meeting-notes.md` 生成纪要草稿，标出歧义和待确认项。
3. 用户确认纪要后，登记确认时间，并把有效事项拆成可追溯的收件箱条目。
4. 将准备应用的低风险事项和已获批准的受控事项组成一次 `meeting_minutes.confirm` 工作流；先完整校验，再原子提交。
5. 对尚未获批的受控事项创建变更请求，展示 before/after 和影响，保留为待审批，不混入本次应用。已批准需求的替代使用 `requirement.replacement.propose`，精确 `change_items` 由 Harness 生成；其他范围才由调用方提供结构化变更。
6. 每个已应用条目记录目标 ID 和应用时间，目标记录保留会议来源 ID。
7. 同一工作流写一条精简活动；提交后重建甘特图和索引，再运行 lint。任一步失败时整体回滚，并说明未应用原因。

若用户只要求整理草稿，不要提前更新需求、计划或决定状态。若用户明确要求“确认并同步项目”，完成纪要后继续执行上述联动，不把命令交给项目经理。

## 输出摘要

交付纪要时说明：

- 纪要当前是草稿、待确认还是已确认；
- 已同步哪些需求、任务、预测日期、风险、决定或交付物；
- 哪些事项因缺少负责人、日期、来源或审批仍待确认；
- 是否产生变更请求，以及哪些基线保持未变。
