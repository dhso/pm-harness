# Create and manage deliverables

Read `.harness/references/deliverable-policy.md`, project context, relevant sources, and acceptance criteria.

Before substantial creation, confirm purpose, audience, use context, format, deadline, required messages/data, and review criteria. Use the closest template in `templates/` as a content scaffold, adapting it to the actual need.

For formal reports, use `pm-communication` to preserve facts while making the narrative concise and natural; this Skill continues to own the file, version, review, and delivery lifecycle.

Register the deliverable before or with the first draft. Work under `deliverables/current/`; use clear stable filenames and increment versions. Never overwrite an approved final.

For DOCX, XLSX, or PPTX, use OfficeCLI when available. Validate structure and issues, and render a temporary preview when visual quality matters. Keep render output outside Git.

Update status accurately through the typed record operation: creation is not delivery, delivery is not acceptance. Approval and acceptance require an active stakeholder with the matching structured scope plus the user's confirmation that the business event occurred. Revising approved content requires an approved change request and a new version/supersession chain.

Close out with the file path, checks performed, current lifecycle state, remaining review actions, and index updates.
