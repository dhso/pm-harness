# 分析规划

## 从决策倒推

把请求改写为“谁在什么时间前，需要据此选择什么行动”。先查已有证据；目标或口径不明确时只问最影响路径的问题。客户只问“能分析什么”时，先给少量高价值方向和各自能支持的决定，不先索取全库。

为每个重要问题定义：待验证假设、分析对象与粒度、指标口径、数据需求、方法、交付结果和判断条件。数据可用性未核验时标为候选计划，不承诺一定能回答。

## 指标口径

只展开本次用到的指标，写清：

- 业务含义、分子/分母、单位、统计粒度及去重键；
- 纳入/排除条件、事件时间或入库时间、时区和区间边界；
- 数据来源、刷新延迟、成熟周期、比较基准与护栏指标。

存量、流量、金额、转化率和留存率不能混用；比率汇总应从分子分母重算，避免平均各组百分比。口径冲突时先列出对判断的影响，不能自行选一个并当成客户共识。

## 选择最小有效方法

| 客户问题 | 优先方法 | 关键核验 |
|---|---|---|
| 发生了什么变化 | 趋势、同环比、结构贡献分解 | 周期完整性、季节性、口径变更 |
| 哪个环节流失 | 漏斗、路径、阶段耗时 | 同一人群、事件顺序、转化窗口 |
| 哪类客户值得投入 | 分群、同期群、价值与成本分析 | 获客时间、留存成熟度、选择偏差 |
| 为什么出现异常 | 分层对照、异常定位、业务事件核对 | 数据质量、结构变化、混杂因素 |
| 方案是否有效 | 随机实验；不可行时评估准实验 | 样本量、对照可比性、干预与护栏 |
| 后续可能怎样 | 基线预测、情景和敏感性分析 | 时间外验证、预测区间、关键假设 |

方法只是候选；不用复杂模型替代清楚的业务问题。不具备因果识别条件时只能给解释假设及验证设计。

## 形成可执行计划

按“数据可用性与质量 → 基线与诊断 → 结论复核 → 建议验证”安排工作。每步只列必要数据、依赖、完成证据和下一步；工期和收益只能是注明依据的估算。负责人、日期、预算和客户承诺不明时留待确认。

无数据库权限时可继续完成指标表、所需数据清单、查询草案和验证设计；不把未运行的 SQL 当成分析证据。要进入项目排期时交接给 `pm-planning`，保留预测与批准基线的区别。

需要文档时参考 `templates/data-analysis-plan.md`；不要求用户填写模板，也不机械填满所有字段。
