# 按风险做质量检查

## 确定检查范围

从本次要作出的决定出发：草稿是否可评审、修改是否解决问题，还是成果是否满足约定标准。优先核对已有标准和可用证据；标准缺失时说明评审依据，只有会改变结论的歧义才询问用户，不把建议标准当成新要求。

- 文字或局部低影响修改：检查修改处和直接受影响的内容。
- 影响业务规则、数据结论或关键交付：覆盖关键成功场景、相关边界与失败场景。
- 正式验收：对照约定标准逐项核对证据，可按需要使用 `templates/acceptance-report.md`；质量检查通过与业务验收分别表述。

这些是检查深度的建议，不新增必填字段、强制文档或状态门禁。

## 选择有判断价值的检查

只选与成果及风险相关的维度，不机械套用整张清单：

| 成果 | 优先检查 |
|---|---|
| 软件或流程 | 关键用户流程、约定业务规则、边界及失败恢复；权限或敏感数据涉及本次范围时再检查 |
| 数据分析 | 指标口径、时间窗口、样本与缺失、关键数字核对、结论是否超出证据；必要时复算关键结果 |
| 咨询方案或报告 | 来源与结论一致性、建议的可执行性、前提和限制、日期数字及正文图表一致性 |
| 文档或 Office 文件 | 内容完整性、阅读顺序、关键页面或表格可读性；公式或版式变更时检查相应计算或呈现 |

记录检查对象或版本、采用的方法、结果和必要证据。明确哪些检查实际执行、哪些只审阅了他人结果、哪些未覆盖；抽样不能表述为全量通过。无法执行检查时说明对结论的限制，继续完成可做的部分。

## 发现与整改

发现应说明现象、对应标准或证据、影响和建议下一步。可复现的问题给出必要条件及预期与实际差异，不以表达偏好代替缺陷。

- 阻塞：有证据表明关键约定标准不满足，影响本次使用或验收。
- 改进：有实际收益，但不妨碍当前约定用途。
- 待验证：证据不足，不能据此声称存在缺陷或已经通过。

需要持续跟踪的实际问题复用问题登记册；尚未发生的不确定影响记为风险。先查询同类记录，更新已有项，字段按 `register.upsert` 契约写入，不为每条润色建议建档。只有需要明确执行跟踪时才关联或创建整改任务；未知负责人或日期保留待确认，不猜测承诺。

整改后先复验原问题，再检查受影响的相邻场景。相关检查已通过且没有新变化时不重复全量检查。尚未关闭的问题说明剩余影响和处理建议；是否接受遗留事项由用户决定，不由 Agent 推断。

## 交付结论

先给评审结论与适用范围，再给关键发现、证据和下一步。没有重要发现时直接说明结果及未覆盖范围；只有需要留存的正式评审或验收才生成报告。涉及项目事实时复用现有写入流程，返回已记录对象和未解决事项，由主流程按 `AGENTS.md` 统一收尾，不额外建立 QA 登记册。
