# 编写项目邮件与汇报

读取项目当前状态、计划、登记册、交付物索引、近期活动，以及用户指定的来源。只加载与本次沟通有关的证据，不为了“写得完整”预读整个知识库。

先确定收件人、沟通目的、期望动作或决定、截止时间、渠道和语气。缺失信息会实质改变正文时，只问一个聚焦问题；否则采用保守假设并标明待确认项。

根据任务读取对应参考：

- 邮件、会议跟进、提醒、升级或决策请求：读取 [邮件写作](references/email.md)。
- 周报、月报、阶段报告、管理层简报或专项报告：读取 [汇报写作](references/report.md)。
- 起草或改写任何对外文本：读取 [说人话与保真](references/plain-language.md)。

## 共同工作方式

1. 建立事实账本：记录主体、动作、对象、日期、数字、范围、条件、完成状态、责任人、风险、决定和来源。
2. 分清事实、判断、建议、承诺和待确认项。缺少证据的数字、因果关系或批准状态不得写成已确认。
3. 先写收件人需要知道的结论、请求和时间，再按影响、依据和下一步补充细节。
4. 用分层结构兼顾简练与完整：正文保留决策所需信息，补充背景、数据表或明细放在后段或附件。
5. 完成保真回读和表达回读，默认只交付一个可直接发送的推荐版本。

短邮件不要硬套标题和模板；长报告必须有摘要和可定位的明细。正式术语可以专业，普通动作应使用常用动词和明确主语。

## 项目护栏

- 草稿、批准、发送、接收回复和验收是不同事件。起草完成不得声称邮件已经发送或报告已经批准。
- 邮件不能自行改变需求、范围、时间基线、预算、交付或验收状态。正文涉及受控事项时，先核对对应批准或明确写为提议。
- 不替收件人作决定，不把“建议”“预计”“正在处理”改写成“决定”“承诺”“已经完成”。
- 不实际发送邮件或调用外部通信服务，除非用户另行明确授权且环境提供对应能力。
- 用户确认已经发送后，记录精简活动；若邮件本身是重要证据，再登记来源定位、时间和关联对象。无需保存每封日常草稿。
- 需要形成正式文件时使用交付物生命周期管理版本、评审、批准和发送状态；普通聊天成稿可直接返回，不制造交付物噪声。

## 默认输出

邮件输出“主题 + 正文”；必要时补充附件清单。报告输出标题、执行摘要、正文和必要附录。除非用户要求，不展示写作过程、多套措辞或冗长的修改说明。

仍有关键缺口时，在成稿后单列极短的“发送前待确认”，不要把占位符藏进自然语言正文。
