# 项目汇报写作

## 选择汇报形态

- 周报或阶段状态：使用 `templates/status-report.md`，围绕结果、偏差、风险和下一阶段。
- 管理层简报或决策材料：使用 `templates/executive-brief.md`，压缩背景，突出业务影响和所需决定。
- 专项分析：使用“执行摘要 → 事实与范围 → 分析 → 建议 → 行动计划 → 附录”。
- 正式文件交付：同时遵守交付物版本、评审、批准和发送状态。

不要把活动流水账当成汇报。每项进展应说明产生的结果或对目标、时间、范围、风险和交付的影响。

## 兼顾精炼与细节

首页或开头必须回答：

- 当前结论或总体状态；
- 与目标或基线相比发生了什么；
- 最大风险或机会；
- 需要受众决定、支持或知晓什么；
- 下一关键日期。

正文保留决策依据：

- 关键成果及证据；
- 里程碑的基线、预测和实际偏差；
- 风险、问题、依赖及负责人；
- 已确认决定与待决策事项；
- 下一阶段行动、负责人和日期。

详细时间线、完整数据表、来源清单和方法说明放入后段或附录。摘要中的数字必须能在正文或来源中找到，正文不能出现摘要没有范围说明的“漂亮数字”。

## 状态表达

状态词必须有可复核含义。若项目没有约定红黄绿标准，优先写事实和偏差，不自行给颜色。

- “完成”需要结果或证据；
- “按计划”需要与基线或当前承诺对照；
- “延期”应写原日期、当前预测和影响；
- “有风险”应写触发条件、概率或紧迫程度、影响和应对；
- “等待支持”应写需要谁在何时提供什么。

预测、目标和承诺分别表述。不要把“计划在周五完成”缩写成“周五完成”，也不要把“预计不影响上线”写成“不会影响上线”。

## 输出检查

- 标题和周期明确；
- 执行摘要能独立阅读；
- 结论先于过程，影响先于活动；
- 决定、行动、负责人和日期能够快速定位；
- 基线、预测和实际没有混写；
- 事实、判断、建议和待确认项有清楚边界；
- 无来源的结论已删除或标记待补；
- 附录承接细节，但正文没有缺少关键请求。

对外汇报还要执行[说人话与保真](plain-language.md)的“对外呈现边界”：删除内部 ID、文件路径和 Harness 字段；将“计划基线”等内部术语改为“原定计划”等受众熟悉的表达，并检查图表、页脚和附件没有残留。
