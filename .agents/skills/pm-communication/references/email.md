# 项目邮件写作

## 先判断邮件任务

- 通知：让收件人知道已经确认的变化或结果。
- 请求：要求提供信息、完成动作或作出决定。
- 跟进：确认会议结论、责任人和截止时间。
- 状态同步：说明进展、偏差、风险和下一步。
- 升级：说明阻塞、业务影响、已尝试动作和需要的支持。
- 交付：说明交付内容、版本、使用方式和确认要求。

一封邮件可以有多个信息点，但应只有一个主要目的。目的冲突时拆分邮件或明确主次。

## 默认结构

主题应让收件人不打开正文也知道项目、事项和期望动作。需要决定或有期限时直接写入主题。

正文通常按以下顺序组织：

1. 第一段：为什么写这封邮件，以及结论、变化或请求。
2. 中段：收件人作出判断所需的事实、影响和依据。
3. 行动：谁在什么时间前做什么；没有负责人时明确待分配。
4. 结尾：需要回复的内容和截止时间。

短邮件可以只有两三段，不需要机械添加“背景、详情、下一步”等标题。信息超过三组、包含多名负责人或多条时间点时再使用项目符号或表格。

## 常见场景

决策请求应包含：要决定什么、为什么现在决定、可选项、建议、影响和最晚决定时间。

风险升级应包含：当前阻塞、已造成或预计造成的影响、已经尝试的动作、需要谁提供什么支持、最晚响应时间。不要用紧张语气代替影响说明。

会议跟进应区分：已确认决定、行动项、负责人、期限和待确认问题。讨论内容不能自动升级为决定。

交付邮件应包含：交付物名称与版本、位置或附件、适用范围、已完成检查、尚有限制，以及希望对方确认的事项。文件已生成不代表已发送或已验收。

## 输出与复核

默认输出：

```text
主题：项目/事项 + 结论或动作 + 必要日期

称呼：

结论、变化或请求。

必要事实与影响。

负责人、动作和日期。

需要对方回复或确认的事项。

署名
```

根据实际关系调整礼貌程度，不虚构姓名、职位、公司、署名或历史沟通。用户未提供署名时可省略或放入发送前待确认。
