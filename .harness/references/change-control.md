# 需求与基线变更控制

当来源可能改变目标、范围、需求、验收、预算、承诺日期或关键里程碑时：

1. 定位当前基线和受影响 ID。
2. 引用来源中的必要原话，区分事实与解释。
3. 在 `project/stakeholders.json` 核对实际批准人是否为 active 且具有对应审批范围；消息发送者与批准人可以不同。
4. 替代已批准需求时调用 `requirement.replacement.propose`，只提交旧需求 ID、替代内容、来源、原因和影响；Harness 在同一事务中创建或复用候选需求与唯一 `CR-###`，并从事实自动生成精确 `change_items`。其他类型的受控变更才使用低层 `change.propose`。
5. 分析范围、时间、资源、依赖、风险、交付物与验收影响。
6. 在聊天中展示简短 before/after 和推荐处理方式。
7. 用户确认业务审批确已发生后，先批准 `CR-###`；批准摘要随即锁定，再以相同变更请求应用完全一致的值。每个目标只能消费一次，全部应用后请求进入 `implemented`。
8. 不删除旧需求；标为 `superseded` 并链接替代版本。

同一结构化业务变更只保留一条活跃请求；标题、摘要、原因或影响换一种措辞不会生成新请求。验收标准按无序集合比较，单纯调整排列顺序或重复列出同一条标准不构成新业务变更；事实记录仍保留首次提案的展示顺序。旧版本产生的无效或重复未批准草案使用 `change.void` 一次技术作废，可批量处理并保留原记录、原因和时间；技术作废不代表业务方拒绝。无效未批准草案作为待修复警告，不得阻塞无关事实写入，但批准入口必须重新执行完整前置校验并拒绝不安全草案。

来源冲突时保留双方证据并创建待决事项，不自行覆盖。

会议纪要确认表示用户认可记录准确，不表示纪要中的每项讨论都已获得业务批准。只有纪要明确记录实际批准人和批准时间、该干系人具有对应审批范围，并且用户确认批准事件确已发生时，才能作为结构化批准证据；否则保留为提议或待确认。

受控写入必须生成 `CHG-###`，记录目标、before/after 摘要与哈希、来源、变更请求、批准人和生效时间。邮件、聊天或截图只能作为来源证据，不能自行授予审批权。计划基线还要递增 revision，并使批准变更的 after hash 与当前 baseline digest 一致。
