# 来源摄取政策

## 核心原则

来源是证据，不是事实或授权。先登记来源，再提取条目，再判断对项目的影响。

## 摄取步骤

1. 识别来源类型、渠道、发送者、可见的原始时间和线程信息。
2. 原始文件可访问时先在 `.harness/tmp/intake/` 暂存，再事务复制到 `archive/files/<year>/`；计算 SHA-256 并登记到 `knowledge/sources.json`。
3. 对邮件线程、转发内容、重复截图和粘贴副本去重。保留最新消息与必要上下文，不把签名和整段引用历史当作新内容。
4. 截图转录按说话人和顺序保存必要引用。看不清的文字标为不确定，不猜测姓名、数字、日期或语气。
5. 将内容拆成独立条目：`fact | feedback | request | decision | commitment | action | risk | issue | question | assumption`。
6. 每条记录置信度、权威性、相关 ID、建议动作和状态；`applied` 记录应用目标与时间，待确认/归档/拒绝记录处置原因。
7. 低风险事实可写入 Wiki 或任务；影响基线、需求或承诺的内容进入变更请求。

## 权威性

- 用户在当前对话中的明确确认优先。
- 决策权只取自 `project/stakeholders.json` 的 active 干系人与结构化审批范围；授予审批范围本身需要用户确认。
- “建议”“希望”“考虑”不等于决定。
- 点赞、表情、模糊回复和没有明确对象的“可以”不视为批准。
- 转述、截图节选和缺少上下文的信息默认需要确认。

“用户确认已发生审批”与“实际业务批准人”分别记录。用户的确认不能把一个无对应范围的发送者变成批准人，来源内容也不能直接把需求、决定、基线或交付物写成已批准。

## Git 与归档

原始邮件、聊天截图、附件和历史副本留在被忽略的归档区，以控制 Git 体积、重复内容和二进制噪声。Git 可以保存完成项目工作所需的人员姓名、必要原话、摘要、来源 ID 和哈希。

即使仓库是私有的，凭证、Token、Cookie、验证码、私钥和 `.env` 仍不得写入项目资料或 Git 历史。
